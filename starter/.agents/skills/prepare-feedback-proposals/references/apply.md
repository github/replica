# Apply approved guidance

Enter only after the user explicitly approves identified, displayed proposals. Approval applies to those exact changes, not every finding in the review.

1. Re-read consumer instructions, the target files and any authority or evidence on which the proposal depends. Compare relevant content with the displayed before-state, including the context that made the change applicable. Preserve unrelated work. Changed wording, conflicting proposals, new restrictions or disputed evidence require a revised proposal and renewed approval before affected edits. Never silently broaden an approved patch to make it apply.
2. Apply only the approved guidance edits in the current consumer repository. Preserve the canonical owner's conditions, exceptions, authority labels and relevant links. Keep private review text and artifacts outside tracked files. Leave environment code, templates, skills, configuration, prototype UI and Hub records unchanged.
3. Run the repository's applicable documentation checks and inspect the final diff against approved proposals. Report failures explicitly. Static checks prove document structure, not whether future agents will follow the guidance; do not claim the underlying design issue is fixed or prevented.
4. Report applied proposal IDs and changed paths, with rejected, deferred or blocked proposals distinguished. Leave edits uncommitted unless the user separately requests a commit. Publishing, scheduling and Hub acceptance need their own explicit requests.

If an edit fails after other approved edits succeeded, report exactly what changed and what remains unapplied. Do not undo unrelated work or describe a partial application as complete.
