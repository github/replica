# Build previews

The preview layer consumes the shared `BuildArtifact` contract: each immutable package file has a `kind`, package-relative `path`, opaque artifact-storage `storageKey`, and `byteLength`. Build producers write the bytes through `ArtifactStorage`, then commit those records with the successful Build. Preview serving does not discover repositories, run Builds, or [import GitHub artifacts](github-actions-builds.md).

## Private prototype service

The optional private reader serves every eligible successful GitHub prototype Build from one shared address. The Build page can play the selected Build inline, and **Open private preview in new tab** opens that exact Build in one click without a confirmation page or changing permissions. Use the private Hub review link below to share from the prototype page. Each recipient must sign in to Hub and already have access. A reader URL does not grant access. Without a reader session, it returns 404 unless the prototype's own navigation can renew access as described below.

Launch and renewal require the [protected HTTPS Hub session cookie](authentication.md#browser-session). If you signed in before Hub started issuing it, sign out and back in, then open the Build again. On HTTPS, Hub ignores the older unprotected session cookie for every request, so turning the reader off later does not let a same-site prototype set a session cookie Hub accepts.

Each Build has its own mount path, `/previews/github/<githubRepositoryId>/<owningWorkflowRunId>/`. The run ID is the workflow run that owns the retained dist, not a later screenshot or retry run. Hub does not offer a private preview if the run identifies more than one Build in the repository, and it checks the exact Build ID again at launch, handoff, exchange and every file request. Hub offers it only for a ready publication record. A request for another Build at the same path returns 404. Compiled output must already use the full mount path for its router and assets. Set the build or publish action's `base-path` input to the same value to record it in `dist/replica-preview-base.json`; use the same path for a separate screenshot job. The action does not recompile or rewrite the bundle. Local Builds, templates, and Builds missing the matching marker are not eligible. The reader serves only `dist/`, with an entry-point fallback for extensionless document routes. Existing Build links, reviews, screenshots, and public link revocation are unchanged. Existing isolated preview hosts resolve a declared mount within the already authorized Build; root-based Builds still use their original paths.

### Runtime settings

| Setting                              | Hub                                        | Reader                                      |
| ------------------------------------ | ------------------------------------------ | ------------------------------------------- |
| `HUB_PRIVATE_PREVIEW_ENABLED`        | Set to `true` to opt in; unset by default  | Must be `true` to start                     |
| `HUB_APPLICATION_ORIGIN`             | Exact public HTTPS origin                  | Same, for launch and authority calls        |
| `HUB_PRIVATE_PREVIEW_ORIGIN`         | Exact public HTTPS reader origin           | Same, for browser ingress                   |
| `HUB_PRIVATE_PREVIEW_READER_SECRET`  | Dedicated random 32-byte base64url secret  | Same secret; not a Hub session signing key  |
| `HUB_PRIVATE_PREVIEW_INLINE_ENABLED` | `true` to play eligible Builds inline      | Same value, so the reader allows framing    |
| `PORT`, `HOST`                       | Normal Hub settings                        | Defaults to `3002`, `127.0.0.1`             |
| Trusted proxy hops                   | `HUB_TRUSTED_PROXY_HOPS` (1–10)            | `PRIVATE_PREVIEW_TRUSTED_PROXY_HOPS` (1–10) |
| Artifact storage                     | Ordinary artifacts                         | Dedicated `private-preview-artifacts`       |

Use the compiled `npm run start:preview-reader` command in a separate service. For local reader checks, use `npm run dev:preview-reader` and a dedicated read-only filesystem directory. The reader does not load a Hub `.env`, initialize Prisma, or use a database, GitHub App, or Hub session signing credentials. For Azure, set the reader's `AZURE_STORAGE_ACCOUNT` and `AZURE_STORAGE_CONTAINER` to the same destination as the [import worker](artifact-storage.md#private-preview-output). Give the reader's separate managed identity one `Storage Blob Data Reader` assignment on that container, conditioned to deny blob listing, and never access to the ordinary artifacts container. The reader reads each published Build by the opaque key Hub returns, so it never needs to list or write blobs. In the Azure reference installation, the setup wizard provisions the reader, its identity and grants, and these settings on both services; see [private prototype service](../../infrastructure/README.md#private-prototype-service).

The standalone link and Hub authorization require a ready publication record for the exact Build. A compatible marker alone does not make a Build ready. The writer is independently opt-in and does not backfill automatically. See [Make Builds playable](#make-builds-playable) to publish new Builds or prepare a retained one. The migration leaves previous Builds, ordinary previews, screenshots, and reviews unchanged. Keep the account and dedicated container fixed when using existing publication records: moving the reader does not move the published bytes.

Run the reader on a different hostname on the same site as Hub. For example, Hub at `replica.example.com` can use `preview.replica.example.com` with a fixed custom hostname and managed certificate, or two generated Container Apps hostnames can be used. Hub refuses to start with the same hostname or another site, using the full Public Suffix List as browsers do. Wildcard DNS and certificates are not needed. Both services accept requests only on their configured external HTTPS host. A deployment that terminates TLS at a proxy must prevent direct access to either listening port and overwrite forwarded headers at the controlled ingress. Only then configure its exact hop count. The reader's direct health probe can use TCP; its `/health` HTTP endpoint requires the same trusted HTTPS ingress as other routes.

When upgrading an installation that already ran the initial private preview migration, coordinate the forward migration with the Hub API upgrade. It preserves access rows and renames their table. The previous Hub API cannot serve private previews against the updated table.

### Make Builds playable

A Build plays in the private service only after the writer copies its served `dist/` files into the dedicated private container and marks it ready. Two paths do this. Both reuse the [import worker's writer](artifact-storage.md#private-preview-output) and never contact GitHub, rebuild, or change the ordinary Build, its artifacts, screenshots, or reviews.

**New Builds.** Enable each repository on the import worker with `HUB_PRIVATE_PREVIEW_WRITE_ENABLED=true`, `HUB_PRIVATE_PREVIEW_WRITE_REPOSITORY_ID` set to one or more comma-separated numeric GitHub repository IDs, and `HUB_PRIVATE_PREVIEW_WRITE_CONTAINER=private-preview-artifacts`. After an ordinary import, a compatible Build on a `proto/*` branch of an enabled repository is published. Other branches, the default branch, local repositories, and repositories not in the list import normally and are not published. Publishing a site from the same repository, such as a separate Azure deployment, is unaffected.

**Retained Builds.** An operator can prepare one already-imported Build whose publication was never set. It is not automatic. Confirm the Build's numeric repository ID, owning workflow run ID, Build UUID, and retained `sha256:` dist digest from the Build's database record, then run from `hub/` in the importer's runtime environment:

```sh
npm run --silent private-preview:replay -- \
  --repository-id GITHUB_NUMERIC_REPOSITORY_ID --run-id OWNING_RUN_ID \
  --build-id BUILD_UUID --prepare-dist-digest sha256:RETAINED_DIST_DIGEST
```

In a built image, use `npm run --silent start:private-preview:replay --` with the same arguments. The writer must be enabled for that repository. The Build must be successful, on a `proto/*` branch, the only Build for that owning run, and record the given digest. Before changing anything, the writer reads every retained file from ordinary storage, checks each size, the base-path marker for that exact repository and run, and the complete dist digest. Only then does it mark the Build pending and copy files. Each copy is a create-only write; an existing object is accepted only when its bytes match, and is never overwritten. The Build becomes ready only after every served file is written or verified. Run the command once per Build.

The command writes one `ready` JSON line to stdout on success. A nonzero exit means it skipped the Build; its warning names the stage and reason described in [replay](artifact-storage.md#replay-a-pending-private-preview). A digest, marker, run, or Build mismatch changes nothing. A copy failure after preparation leaves the Build pending and unplayable; fix the cause and rerun the same command. Rerunning for a ready Build makes no storage calls and reports `ready` again.

### Authorization and isolation

Hub owns the launch at `/api/private-preview/launch/<githubRepositoryId>/<owningWorkflowRunId>`. Private launch supports GitHub sessions and explicitly configured local administrator sessions, not Entra sessions. The launch accepts only same-origin Hub form posts; opening it as a link returns 404. The Build page's new-tab button posts the selected Build's ID from the viewer's Hub session. Hub checks current access to that exact Build and sends a signed launch intent, bound to the Hub session and a 30-second database deadline, to the reader in a form body.

The reader gives each launch its own short-lived, host-only browser challenge, so opening several tabs does not replace another launch's challenge. It limits pending launches per browser. It returns the signed state to Hub with a same-site, top-level form post, which carries the protected Hub session cookie. Hub accepts that return only from the exact reader origin as a top-level navigation. It checks the session, the exact Build and current access again, then issues a one-use handoff tied to the Build, Hub session, reader, and challenge. The database keeps the launch's unique ID until its deadline, including across exchange, so one launch cannot issue a second handoff. Fixed Hub and reader forms submit each step without a click or serving prototype HTML. Proofs, grants, and session credentials do not enter link URLs.

The reader exchanges the handoff with Hub and sets secure, HTTP-only, host-only cookies for that exact Build. They use the Build's mount path, so a browser sends only that Build's cookies after opening many Builds. The reader signs each cookie for its Build and for a random `__Host-` browser cookie that only the reader can set. Another host on the site can add a same-named cookie, even one genuinely issued to another browser, but the reader ignores it, so it cannot select another account's session. The reader session lasts eight hours, measured by the database. A separate signed Build marker lasts 24 hours. It identifies which Build this browser opened, but cannot grant access or open files. The reader clears the launch challenge after a successful exchange.

When the reader session is missing, expired, or its Hub session has ended, a top-level navigation from the prototype itself renews access without a click. The reader signs a 30-second state for the marked Build and the requested path and query, binds it to a host-only challenge cookie, and returns it to Hub in the same way as a launch. Hub checks current access to that exact Build before issuing a handoff with its own 30-second database deadline. The reader accepts the handoff only before its signed state expires, then opens the requested route. If the Hub session has ended, renewal goes to normal Hub sign-in. The reader does not renew for asset requests, outside or typed navigations, Builds this browser has not opened, or denied access; those return 404.

The reader asks Hub once per file request, before its bounded file read, and still checks the stored length. Hub checks the current session, exact Build and repository scope before and after the file lookup. Conditional requests do not bypass authorization. Responses are not cached. If that check finds an ended Hub session, a lost Build or scope, a GitHub denial, or an unavailable authority, the reader returns no bytes. A file whose check passed is still served if access ends during its bounded read. Only the reader sends credentials to the server-to-server endpoints; those endpoints do not enable browser CORS. Keep request bodies, cookies, authorization headers and redirect details out of ingress logs.

Launch, handoff and renewal always check current GitHub repository permission. For file requests, Hub remembers an allowed permission result for 5 minutes in memory on each Hub replica. The result belongs to one Hub session, viewer identity, repository and exact Build. Concurrent file requests for the same viewer and Build share one in-flight check. Hub never remembers a denial or an error. It forgets the results when the Hub session ends. It forgets a repository's results when GitHub denies access, the Build changes, or repository scope is lost. That also cancels the session's file checks still in progress for the repository. **Revoked GitHub access can keep serving files from a Build the viewer already opened for up to 5 minutes.** Ending the viewer's Hub session stops file reads on the next request. The Build page decides whether to offer inline playback from database state only; it does not call GitHub while holding a prototype or metadata lock.

### Inline playback

With inline playback enabled, the authorized Build detail response includes an inline URL for each private-ready Build, `/api/private-preview/inline/<githubRepositoryId>/<owningWorkflowRunId>/<buildId>`. The Build page frames that Hub launch shell only when the Build has no legacy Build-specific preview, which keeps review pins, Controls and route tracking. Without inline playback, the page keeps the saved screenshot and new-tab button, and the new-tab button remains beside inline playback. A Build page deep link opens inline playback at its requested route, if that route stays inside the Build's mount. Hub cannot see routes inside inline playback, so its copy action copies a link to this Build instead of the current route; a selected conversation still copies its own route.

The launch shell is the only Hub response that may be framed. It requires a same-origin iframe request, checks current access to the exact Build, and sets `frame-ancestors` to the exact Hub origin. Its policy allows only its own nonce script and styles, same-origin requests, a reader frame and forms to the reader. While the reader is enabled, every other Hub response, including Hub pages, sends `frame-ancestors 'none'`; legacy Build origins keep their own Hub-only framing policy. The shell starts the same signed launch in a nested reader frame. Instead of returning to Hub with a form, the reader posts each signed launch or renewal state to the shell's exact Hub origin. The shell accepts messages only from its reader frame and origin, then requests each handoff with a same-origin Hub request for that exact Build. Hub returns 401 when the Hub session has ended, and the shell shows a sign-in and new-tab message. If the shell itself cannot start, Hub returns a short frameable message for an ended session, a denied or incompatible Build, or an unavailable authority. If the reader frame loads without sending a signed state within a few seconds, for example after its pending-launch limit, the shell replaces it with a new-tab message.

The reader allows framing only for iframe requests when inline playback is enabled, and only by the exact Hub origin. Top-level reader documents keep `frame-ancestors 'none'`. Both the Build page frame and the nested reader frame use the same sandbox as legacy preview frames: scripts, their own origin, forms, dialogs, popups and downloads. The reader's `form-action 'none'` still blocks form navigation, and neither frame may navigate the Hub page. Inline frames do not run the review bridge or Controls.

### Shared address and site

The reader is separate from Hub, **not** per-Build browser isolation. One shared address serves every Build. Active content on that address can act as the reader origin, including loading any other Build the same viewer can open in that browser. Prototypes also share that origin's browser storage. Renewal widens this exposure. The reader cannot tell which Build started a same-origin navigation, so content from any Build can renew another Build this browser opened in the last 24 hours, while the viewer's Hub session lasts and Hub still grants access. Each renewal starts a new eight-hour reader session. Worker use is disabled. Bundles that depend on an HTML `<base>` element are unsupported; compile the router and asset paths for the mount instead.

Hub stays on its own origin and keeps its cookies host-only, but the reader shares its site. SameSite cookies therefore no longer show that a request came from Hub. While the reader is enabled, Hub rejects every API request that a browser marks as same-site, except the reader's signed launch return, denies framing of its pages so prototype code cannot frame a signed-in Hub page. The prototype detail request records a first-view introduction only when the browser marks it as same-origin. Hub's other exact-origin request checks are unchanged.

Keep the reader off until the deployment and browser handoff are verified and the shared-address tradeoff is accepted. Embedded review, Controls, and interactive templates still use the legacy Build-specific origins below. Extending the private reader to support those workflows requires a separately reviewed authorization design and end-to-end validation with normal supported-browser privacy settings.

## Legacy isolated access flow

The prototype response keeps Build selection on `/repositories/:repositoryId/prototypes/:prototypeId?build=N`. A Build with `dist/index.html` receives an authenticated Hub access URL when `HUB_PREVIEW_ORIGIN` is configured.

Build screenshots do not need the isolated origin. When Hub has artifact storage, prototype tiles and prototype details receive screenshot URLs at `/api/repositories/:repositoryId/prototypes/:prototypeId/builds/:buildNumber/screenshots/:size` on the Hub origin. Hub checks the live session and repository visibility, then serves the stored bytes as `image/png`. Import checks only the PNG signature, so the response headers provide the isolation: `private, no-store`, `nosniff`, a same-origin resource policy, and a sandboxing content security policy. Screenshots therefore appear in installations, such as Azure Container Apps, that do not configure wildcard preview hosts.

Preview access follows these steps:

1. The browser requests the access URL on the Hub origin with its Hub session.
2. Hub checks the live session again after locating the requested successful Build artifact.
3. Hub issues a 30-second encrypted grant and redirects to that Build's wildcard preview origin.
4. The preview origin exchanges the grant for a 15-minute, host-only, HTTP-only cookie.
5. Preview files are read by opaque storage key. Hub session cookies and provider credentials never enter the Build origin.

`HUB_PREVIEW_ORIGIN` is the wildcard base. For example, `https://preview.example.net` serves one Build from `https://<build-uuid>.preview.example.net` while Hub runs on `https://hub.example.com`. Outside local development, the preview and Hub origins must use separate registrable domains so untrusted preview content cannot shadow Hub cookies through a parent domain. Operators must configure wildcard DNS and TLS. Local development uses `http://preview.localhost:3001`.

The [template catalog](frontend.md#create-templates-and-welcome) selects one successful Build from the repository's current default branch. Its preview and declared desktop screenshots use `/api/repositories/:repositoryId/template-builds/:buildId/access` so each request stays on that snapshot. Hub rechecks repository visibility before granting access and on the Build origin. A template grant cannot open a prototype Build, and a template preview does not enable the review bridge. The dark theme uses the saved dark screenshot when present and falls back to the light one.

If the isolated frame does not answer Hub, the review and template pages show a fallback with a saved screenshot when one is available and a top-level link. Opening a screenshot in its own tab can help when embedded requests are blocked. The template's create or copy-prompt actions do not depend on frame readiness.

With the optional private reader configured, the prototype view offers a separate **Copy private Hub link** action. It points to the Hub prototype page, not to the reader or a grant. A latest link follows the current successful Build and omits the previous Build's verified mount from the page route. A pinned link includes its Build number. Copying an open saved conversation pins that conversation's original Build, route and thread ID. If the exact route cannot be opened through the Build access endpoint, Hub reports that it cannot be copied instead of substituting the Build's start page. Hub checks the recipient's existing access. **Open private preview in new tab** opens the selected Build in one click at its configured start page.

## File behavior

Package paths remain relative and may not contain empty, dot, dot-dot, control, surrogate, absolute, or backslash segments. `/` serves `dist/index.html`, and directory-style requests first look for their nested `index.html`. A missing extensionless browser route falls back to the application entry point. A dotted route receives the same fallback only when the saved template manifest declares it; missing asset paths return 404. The prototype's normalized start page is used after grant exchange.

Content types come from the checked package path, with unknown extensions served as `application/octet-stream`. HTML is private and revalidated. Immutable assets use a private one-year cache. Template screenshots, and screenshots requested through a Build access grant, are served from their package paths through the same Build authorization.

Each serving process has a 100 MiB source-byte allowance for preview reads. Hub shares its allowance across legacy Build origins, template previews, public links, and Hub-origin Build screenshots. The standalone reader has its own allowance. The serving process reserves each file's recorded size before reading storage and keeps that reservation until the read settles and the HTTP response finishes or disconnects. A request returns 503 without reading the file when the allowance is full. Small and empty files reserve at least 64 KiB each. Temporary template-manifest reads release their reservation before reading the selected HTML file.

This allowance bounds concurrent buffered preview files, not total process memory. Storage downloads can hold chunks and their combined buffer at once, and HTML bridge injection needs additional strings and encoded bytes. Imports and other runtime work need separate headroom within the deployment's memory allocation.

HTML responses inject the hosted preview bridge. The bridge installs the shared Controls engine and bindings, which load that Build's `/controls.replica.json`, and reports review element or area selections to the authenticated parent page. Hub checks the Build origin, frame, message shape and current navigation handshake before using review messages. Navigation invalidates pending selections. A bridge message cannot save review data: only the Hub composer submits a create request, and the [review API](review-collaboration.md#product-api) checks current authority and scopes the Build and thread before writes. The bridge does not write artifacts or receive Hub session cookies. The generated Controls bridge is checked by `npm run controls:assets:check`.

Revalidated preview HTML loads `/__replica/bridge/v3.js`. Older asset URLs keep the existing preview access checks. The current bridge still answers the original readiness request without a navigation ID for older Hub tabs. Current Hub tabs request navigation-scoped readiness on isolated Build origins and do not accept replies without the matching ID. A separate scoped message reports the exact mount verified while serving the document; it does not change the readiness reply for older tabs. Hub restores section fragments after readiness and passes hash-router routes through unchanged. If an older server cannot supply the readiness handshake, the preview uses the existing screenshot or tab fallback.

## Browser boundary

Each Build has a separate origin. Responses deny MIME sniffing and referrers, restrict framing to the configured Hub origin, keep resources same-origin, disable camera, microphone, and geolocation, and apply a same-origin content security policy. The iframe remains sandboxed by the Hub frontend. Preview routes return 404 on the Hub host, an unknown Build host, an invalid or expired grant, a mismatched Build cookie, and unsafe paths.

The first version does not add Canvas pairing, standalone Build pages, hosted repository discovery, hosted Build execution, or GitHub App setup.

Local mode also supports [Build-pinned public share links](share-links.md). They reuse this file-serving path and Build-specific origin, but exchange a purpose-bound public grant for a separate purpose-bound `replica_share_preview` cookie. Grants and cookies cannot be exchanged. Public requests recheck the saved link and deployment setting before and after artifact reads. They never accept a Hub session as public authorization or expose repository and review data.
